# Setup Tab Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Setup tab on player profiles showing keyboard, tablet, mouse, monitor, in-game and PC cards, edited per card by the owner or an admin.

**Architecture:** One optional `setup` object on `players`. A shared `PATCH /api/players/[id]/setup` endpoint validates with valibot and calls `players.updateSetup`, which re-checks permission and merges only the sent cards inside the mutation. The panel places cards with a pure layout function (`full`/`half`/`tall`) and each card adapts its insides with Tailwind v4 container queries.

**Tech Stack:** SvelteKit 2 + Svelte 5 runes, Convex, valibot, Tailwind v4, bits-ui/shadcn-svelte, vitest.

**Spec:** `docs/superpowers/specs/2026-11-06-setup-tab-design.md`

## Global Constraints

- Models and names display exactly as typed; no uppercasing anywhere in part 3.
- Empty means absent: trimmed empty strings, `null`/blank numbers and empty-name storage rows are dropped; an empty card is removed; an empty `setup` is removed.
- `null` in a patch removes that card (or clears `main_input`).
- Validation ranges and the "<field> <message>" error format: exactly the table in the spec's "Validation ranges".
- Storage kind labels: "NVMe SSD", "SATA SSD", "HDD".
- Empty model → "Unknown"; empty value → "–".
- No photos, no `device_id`, no devices table (part 4).
- Commits: plain conventional messages, no Co-Authored-By trailer (user rule).
- Simple code: 2–3 repetitions are fine; no abstraction layers without payoff.

## Review Focus

- A number input cleared by the user arrives as `null` and must remove the field, never store `0`.
- An admin edits a player who has never logged in (no `authUsers` row): allowed. A logged-in non-admin editing someone else's setup: 403 at the endpoint and in Convex.
- Turning "This is my main input" off on the Tablet card while `main_input` is `"mouse"` must not clear it.
- Tablet values where the area is bigger than the full size, or the centre puts the area past an edge: the diagram stays inside the tablet outline (clamped), never overflows.
- Owner and admin saving different cards at the same moment: both cards survive.

Each line has a test in the task that owns the code (Tasks 1, 2, 3, 5).

  - `null card stays null`: `{ tablet: null }` → `{ tablet: null }`.
  - `main_input accepts tablet, mouse, null`; rejects `"keyboard"`.
  - `rejects out-of-range values`: `actuation: 0`, `actuation: 4.5`, `dpi: 1.5`, `audio_offset_ms: 1001` each fail; issue message contains "must be".
  - `accepts negative audio offset`: `-12` passes.
  - `drops storage rows with an empty name`: `[{ kind: "nvme", name: " " }, { kind: "hdd", name: "WD Blue" }]` → one row.
  - `rejects 9 storage rows` and `rejects an unknown storage kind ("m2")`.
  - `rejects unknown card keys` (`{ speakers: {} }`) — use `v.strictObject` at the top level.
  - `rejects text over 100 characters`.

    - all six → `keyboard:full, tablet:tall, mouse:half, monitor:half, in_game:full, pc:full`
